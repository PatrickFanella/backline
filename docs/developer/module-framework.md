# Bot modules and core commands

The bot entrypoint starts the Gateway runtime in `backend/src/bot/startup.ts`. Existing event collectors live in `collectors.ts`; importing them does not log in. The module registry validates configuration, checks installation state and configuration versions, and contains event failures. New or disabled modules do not receive collector events. Existing history remains in the database.

Each module declares its configuration schema/version, required Discord permissions and intents, commands, and pending-job policy. Activity collection and trusted operator plugin event dispatch are initially disabled for every server. Activity is optional; core commands need only the Guilds intent. The registry checks current settings on each event, so disabling a module takes effect without restart. Plugin initialization remains trusted operator code; module gates are not a sandbox for arbitrary plugins.

The guild-only commands are `/help`, `/setup`, `/settings module enabled`, and `/status`. Replies are ephemeral. The router acknowledges before database access and returns a clear response for unknown components, unavailable installations and failed actions. Configuration requires a fresh member fetch and current owner, Administrator or Manage Server permission. Setup reports missing bot permissions and Gateway intents.

Enable `BOT_ACTIVITY_INTENTS=true` only when the application has the required intents configured in the Discord Developer Portal. Restart the bot, then use `/settings` to opt a server into activity. Without the runtime intents flag, both command and REST configuration reject enabling activity. `BOT_GUILD_IDS` remains an optional operator restriction; unset it for independent installation after that release gate is qualified.

Set `BOT_REGISTER_COMMANDS=true` for an explicit command-registration run. It creates or updates only the four named commands in eligible installed servers and preserves other commands. Normal restarts leave Discord command registration unchanged. Registration is server-scoped during this pilot; global public registration remains part of the release gate.

The authenticated REST adapter provides `GET /api/guilds/:guildId/modules` and `PUT /api/guilds/:guildId/modules/:moduleId`, with `{ "enabled": false, "config": {} }`. JWTs and API keys require the same current server authorization. This adapter and slash commands use the same persisted configuration; the dashboard UI is F06.
