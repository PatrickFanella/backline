# Durable API-to-bot actions

API and bot processes share PostgreSQL job records. They do not share an in-memory queue. Each action has a server, requesting account, idempotency key, schedule, expiry, retry limit, lease owner, attempt history and persisted outcome. A server can hold at most 1,000 pending, leased or uncertain actions. Concurrent enqueue calls with one server/key retain the original actor, payload and schedule.

Workers claim one due action using a transaction and `FOR UPDATE SKIP LOCKED`. The lease lasts 30 seconds and is renewed during execution. A stale owner cannot record completion after the lease expires or ownership changes. The worker rechecks authorization before execution. Disabled modules cancel queued actions when the worker reaches them; existing in-flight Discord requests can still complete. Modules currently declare a cancel policy. Pause/resume is not implemented.

Handlers return DELIVERED with a provider identifier or result, RETRY only for a known non-delivery, or a terminal failure/cancellation. Retries use bounded exponential backoff and stop at the configured attempt limit or expiry. An exception or expired worker lease produces RECONCILE. Such actions are held, rather than automatically repeating a Discord mutation. A handler-specific reconciliation method must establish delivery or safe retry. This does not promise exactly-once external effects: Discord and PostgreSQL cannot commit one transaction together.

The first bot adapter is the read-only `server-status` action. It requires current Discord management permission through the requesting account's OAuth authorization, then fetches the server and bot member from Discord and persists the bot permissions and Gateway state. An uncertain status read can be retried safely; the bot polling adapter reconciles these reads automatically. Future moderation and message handlers need provider-specific reconciliation and current bot/actor permission and hierarchy checks.

`POST /api/guilds/:guildId/jobs/status` accepts an idempotencyKey and optional ISO runAt, up to 30 days ahead. It returns HTTP 202 with the persisted action ID and state. `GET /api/guilds/:guildId/jobs/:jobId` returns the record and attempt history. Both paths require current server authorization for JWTs or API keys. A job from another server returns 404. The bot polls once per second while `BOT_RUN_JOBS=true` and waits for its current job before graceful shutdown.
