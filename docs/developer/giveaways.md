# Giveaways

Giveaways are an opt-in module. Enable them in server settings after checking the bot's View Channel, Send Messages, Embed Links and Read Message History permissions in the announcement channel. The module does not require presence or message-content intents.

Use `/giveaway create` to choose a prize description, text channel, deadline, winner count, optional required role and minimum membership age. The dashboard also accepts up to five required roles. Members enter or withdraw through the announcement buttons. Entries are unique per member and close at the deadline. Bots cannot enter; current role membership and server membership age are checked at entry and again at every draw. Members who leave or lose a required role are excluded. An unavailable eligibility read holds the draw rather than treating the member as ineligible.

The dashboard queues creation and draw actions. Queued work is not confirmed Discord delivery: use **Check action result** and the recorded giveaway history. Command and worker actions recheck the actor's current Manage Server permission and application access. If the original creator loses permission, another current manager can use `/giveaway draw`, or **Queue draw** in the dashboard, after the deadline.

Each draw commits one cryptographically selected winner set before editing the recorded announcement. Concurrent initial draws return the same persisted round. Reconciliation can repeat the edit to that message with the same result. Rerolls exclude all previous winners, preserve earlier rounds, and wait until the previous announcement is delivered. Ten rerolls are allowed. `/giveaway history` and the dashboard show each round and its announcement state. Winner displays do not send mention notifications.

Initial announcement creation has a different recovery boundary. If a send has an uncertain outcome, the reserved giveaway remains `CREATING` and the action remains held. A retry does not send a second announcement. Investigate the recorded channel and action before resolving that hold. Disabling the module cancels scheduled work; reenabling it does not automatically resurrect cancelled actions. Pending draw jobs survive process restarts, and the recovery scan repairs a missing job for an open giveaway.

Limits are per server: at most 25 active or held giveaways, 1,000 entries per giveaway, ten winners per draw, and a deadline within 30 days. Defaults are ten active giveaways, 500 entries and 30 days of history after the deadline. New giveaways capture the configured retention period, bounded to 1–90 days. Expiry deletes completed giveaway entries and rounds plus completed related jobs. Uncertain initial announcements remain held and count against the active quota.

The additive `20261005001000_giveaways` migration introduces giveaway, entry and draw tables. It does not rewrite existing histories; an older application can ignore these tables during code rollback. Deploy the migration before starting the updated API or worker.

Qualification: PostgreSQL checks cover competing draws, duplicate entries, withdrawal, role loss, member departure, quotas, held sends, repeatable result edits, missing-job recovery, dashboard queue idempotency, revoked application access and denied cross-server API access. Existing command, module and durable-job tests are included in the focused run. Frontend tests cover disabled modules, queued versus delivered actions and uncertain outcomes. All twelve migrations also passed on a new empty disposable database, which was removed afterward.

Live giveaway delivery and natural member button use remain unqualified. The first disposable-channel attempt was denied by Discord with missing permissions; the disposable member must rejoin the approved server where the bot has the required test-channel permissions. These local checks do not prove hosted CI, a real process restart at the deadline, owner browser creation, or sustained pilot operation.
