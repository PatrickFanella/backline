# Selective server restore

The recovery module adds `/restore preview|apply|status|map`. A preview compares a retained snapshot with freshly read server structure. Supply comma-separated original role/channel IDs to select at most twenty resources, or omit `resources` for comparison only. The dashboard lists every selected change with before/after fields, step state and target ID; downloading the full plan includes the desired manifest and every compared resource. Role permission names accompany the numeric permission bits.

This restore creates and updates selected ordinary roles, categories, text/announcement channels and voice channels. It performs zero deletions. Include missing categories and ordinary roles with dependent channels. A missing overwrite role/member or parent blocks the channel rather than silently dropping access controls. Member overwrites require current membership, with at most fifty distinct members validated per preview. Everyone, managed, privileged, protected and above-bot roles are skipped. Unsupported channel types and type conversions are skipped. Configured protected IDs, server system/rules/public-update/safety channels and the preview’s command channel are protected. The dashboard can edit protected role/channel IDs.

Restored channels explicitly retain the bot’s View Channel, Manage Channels, Send Messages and Read Message History access. The preview shows these added/adjusted overwrites. Absolute positions, deleted member accounts, role membership, original messages/authors, threads, forums/media/stages, emoji and webhooks are outside application. Captured metadata for these resources does not imply it can reconstruct them. Discord exposes separate [role/channel operations](https://docs.discord.com/developers/resources/guild); it does not offer an atomic server reconstruction transaction.

Previews expire after fifteen minutes. Before application, the current server owner must review the exact plan and submit `confirm:"RESTORE SERVER_ID PREVIEW_ID"` with `/restore apply id:PREVIEW_ID`. This is enforced by fresh Discord owner/member checks and exact string matching. Queueing records the owner in the action job and does not prove application. The bot needs current Manage Roles and Manage Channels. Changed structure or recovery configuration rejects a stale preview. A structure fingerprint is checked again before every step, and the expected fingerprint advances only after a confirmed operation and fresh read.

Each confirmed step persists its target ID and a reusable source-to-target mapping under the server lock. Current permissions, resource protection and dependencies are checked again. A confirmed 4xx rejection pauses the plan; after resolving permissions, the owner can confirm the same fresh plan again, up to five attempts. A lost creation result, failed post-write read or lost worker lease holds the plan without replay. Inspect Discord, use owner-only `/restore map kind:… source:… target:…` for any verified recreated resource, then generate a fresh preview for the remainder. Mappings keep already-created resources from being duplicated by later plans. `/restore status` shows the confirmed/held steps. No restore step deletes a role or channel.

Discord API reads and writes cannot exclude a concurrent administrator changing the server between those requests. Fresh fingerprints reduce that window; operators should avoid concurrent edits during application. A partial restore is visible as partial and does not claim completion. A held creation without a known target cannot be automatically identified from a matching name alone.

Limits are twenty retained plans, twenty selected resources per plan, one thousand mappings per server and three MB per preview. Completed/cancelled plans and their terminal job receipts expire after thirty days; uncertain records are retained for bounded investigation. The shared active-job limit applies. Held readback rotates across jobs, so older held work cannot occupy every reconciliation pass.

## Qualification

Eight PostgreSQL restore checks cover comparisons without writes, current owner/exact confirmation, stale rejection, actual worker application, mapped step receipts, confirmed-rejection resume, lost-creation holds/manual mapping, protected resources, category/child creation with remapped role overwrites and ordinary role updates with reviewed before/after fields. The six snapshot checks run alongside them on a fresh database with twenty-two migrations and seventy-five domain tables. Three planning checks cover privileged/managed/above-bot protection, mapped protected targets, cross-server input and invalid selections. Four dashboard checks cover previews, exact confirmation guidance, unavailable reads and snapshot settings.

App builds, changed-file lint and hosted CI are separate checks. Actual Discord snapshot/restore comparison in a disposable server, owner-session review, natural restart recovery and rollback remain qualification gates. No production restore was applied during implementation.
