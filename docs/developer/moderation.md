# Moderation and case history

Enable `moderation` in server setup or `/settings`. Commands are `/warn`, `/timeout`, `/kick`, `/ban`, `/unban`, `/purge`, and `/cases`. Each action requires a reason. `/warn` records a warning without sending a DM. `/cases` requires current Moderate Members permission.

The dashboard at `/moderation` lists the selected server's last 100 cases and queues actions through PostgreSQL. API reads and submissions require current server management access; execution also fetches the actor and bot from Discord and checks the action's actual permission. Manage Server alone does not permit kicks or bans. Disabling the module cancels queued actions.

Member actions fetch the current target and compare both actor and bot role positions. Equal or higher targets, the server owner, the actor and the bot are protected. The server owner may bypass the actor role comparison; the bot hierarchy still applies. Bans currently require a target who is still a member. Unban verifies the existing ban first. Timeout rejects administrators and accepts 1 to 40,320 minutes. Purge requires channel View Channel, Read Message History and Manage Messages for both actor and bot. It considers at most 100 recent messages and skips pinned messages and messages older than 14 days.

Cases record actor, target or channel, reason, timestamps and outcome. `DELIVERED` means the operation returned successfully, or a local warning was recorded. Purge outcomes contain actual deleted message IDs. `DENIED` records a failed authorization check. `FAILED` records an unavailable precondition or a definite Discord rejection. `UNCERTAIN` means a mutation started but its outcome could not be proved. Do not submit a fresh request to repeat an uncertain mutation.

The server/request pair reserves a case under a PostgreSQL transaction lock before execution. Repeating a slash interaction or queued job returns that same case and never repeats the mutation. A crash can leave a `PENDING` case; this also remains held. Queue leases and case reservation prevent automatic replay. Investigate uncertain cases against Discord audit logs and current state; an absent member alone cannot prove which action removed them. No automatic reconciliation claims delivery from ambiguous state.

Migrate with `prisma migrate deploy`, restart the API and bot on the same database, and register commands explicitly with `BOT_REGISTER_COMMANDS=true`. Command registration upserts names and preserves unrelated commands. Disable the module to stop new execution; keep the additive case table and its history during rollback.

Validation: real PostgreSQL tests cover concurrent duplicate requests, lost responses, actor and bot revocation, role hierarchy, pinned and old-message filtering and input bounds. Dashboard tests cover server scoping and unchanged retry keys. These tests use Discord fixtures and do not establish human slash-command or destructive member delivery. Live evidence belongs in issue C01, separately from these checks.

Live qualification on October 4, 2026 used a disposable PostgreSQL database and server `947948179897327686`. Eleven commands were registered and read back. A self-kick case was denied as a protected target. A purge returned `DELIVERED`, recorded two deleted message IDs, and a subsequent Discord fetch confirmed the disposable message was absent and the pinned fixture remained. The temporary private channel was deleted afterward. The first harness timed out; its owned channel was separately identified and removed before rerunning with a longer deadline. This proves bot-service delivery for purge and a denial path, not human OAuth, slash-command submission, timeout/kick/ban delivery or sustained pilot operation.
